# Polaris 验证池文档规范

## 目标

验证池只沉淀 Polaris 可迁移的验证逻辑，不沉淀某一轮设备的临时结论。新功能进入后，先匹配模块，再生成当前功能的方案、用例、断言和执行映射。

## 模块边界

每个模块描述一种功能意图，例如“唤醒会话”“全半双工”“云控设置”。同一意图允许多个变体，不能把某一设备或某一轮结果当成唯一正确逻辑。

## 必填结构

每个模块必须包含：

1. YAML front matter
   - `module_id`
   - `title`
   - `tags`
   - `source_projects`
2. `## 适用需求特征`
3. `## 变体维度`
4. `## 需求解析字段`
5. `## 验证方案模板`
6. `## 用例模板`
7. `## 断言与证据`
8. `## 执行器映射`
9. `## 回灌规则`

## 变体处理规则

- 先识别功能意图，再选择断言。
- 当前需求、用户澄清和实测证据优先。
- 命中多个互斥变体时标记 `AMBIGUOUS`，用最小探测或向用户澄清收敛。
- 需求没有说明关键维度时，只能生成 TODO/BLOCKED 或探测型用例。
- 项目特定结论不得写成通用规则；只有抽象后的方法才能回灌。

## 输出要求

模块匹配后应生成：功能点清单、命中模块和变体、采用/不采用的逻辑说明、用例和断言、证据路径、需澄清或人工确认项。

## 最终 FAIL 规则

最终 FAIL 只能是固件不满足当前需求，或当前需求自相矛盾/错误。环境、设备、云端、采集、播放、脚本、断言、状态污染等问题必须先收敛。
